# 緊急経路

本番で何かが壊れていて、使える時間は2時間。通常の経路 — 仕様を書き、計画し、18の関所を通し、検収する — は正しい経路ですが、いまは遅すぎます。

`/hora-hotfix` はそのためのもう1本です。**不具合を1つ直し、出し、飛ばしたものを全部書き残します。** 飛ばした分は静かに消えるのではなく、後から実際の作業として戻ってきます。

```
/hora          機能1つ    →  18の関所  →  検収済み
/hora-hotfix   不具合1つ  →  6つの門   →  着地。ただし負債つき
```

**`/hora` はこれを起動しません。** 緊急かどうかは人が決めることなので、`/hora-hotfix` は自分で打ちます。

---

## 何を諦め、何を諦めないか

| | |
|---|---|
| **諦めるもの** | 受入レビュー、ブラウザでの実走、UX監査、シナリオ一覧、バージョン自身の受入基準、`/hora-spec`、`/hora-plan` |
| **残すもの** | 落ちるテスト1本、全リポジトリのユニットテスト全量、触ったファイルの lint、git 規約、記録 |

**時間を食っているのはユニットテストではありません。** 数分で終わり、しかもこの修正が他をどこか壊していないと言える唯一の根拠なので、残します。何時間もかかるのはレビューの方で、後回しにするのはそちらです。

**テスト1本が、その後回しを正直なものにします。** 修正前に落ちたテストが無ければ、「ユニットテストは通っています」は直そうとした不具合について何も言っていません。

---

## 6つの門

```
H1  受理判定  そもそも hotfix に乗るか。「直った」とは何か
H2  再現      落ちるテスト。しかもこの不具合が原因で落ちる
H3  修正      それを通す最小の変更
H4  影響範囲  ユニット全量 + 触った面が強制するもの
H5  記録      .hora/hotfix/<hotfix-id>.md
H6  着地      main へマージし、追従を /hora に渡す
```

各門には通過条件が1つだけあり、前の門が終わるまで次は始まりません。

### H1 — 受理判定

ここで2つのことをします。

**1つめ。そもそも hotfix に乗るか。** 次の6つに当たると乗りません。

- 後方互換でないスキーマ変更 — 何かを落とす・改名する・狭める・上書きする
- 開いている `release/<version>` が未適用のマイグレーションを持つテーブルに触るスキーマ変更
- 他のリポジトリが作っている最中の契約の変更
- 依存の追加・削除・更新
- 新しい operation / 画面 / バックグラウンドジョブ
- ブランチ1本に収まらない作業

**2つめ。「直った」とは何か。** これは人が1文で書きます。他の誰も書けません — 製品がどうあるべきかを述べる文であり、それは人のものだからです。**この1文が、この実行の受入基準のすべてになります。**

### H2 — 再現

**落ちるテストを書きます。しかもこの不具合が原因で落ちること。** 修正の後ではなく、前に書きます。

テストで捕まえられない不具合もあります — 遅いクエリ、本番データでしか出ないもの。その場合は記録に `reproduced: no` と理由を書き、代わりに測定値を載せます。修正前の数字と、修正後の数字です。

### H3 — 修正

**H2 のテストを通す最小の変更だけ。** リファクタリングも、ついでの整理もしません。

### H4 — 影響範囲

全リポジトリのユニットテストを全量。そのうえで、触った面が強制するものを実行します。

| 修正が触ったもの | 飛ばせないもの |
|---|---|
| 認証・認可・呼び出し元のフィルタ | 変更範囲に絞ったセキュリティ監査 |
| 共有コード | ユニット全量。ここでは狭められません |
| DB に書かれるデータ | 不具合が既に書いた行をどうするかの記述 |
| スキーマ | 追加の4手順（後述） |

### H5 — 記録

`.hora/hotfix/<hotfix-id>.md` を書きます。**これが、この実行が飛ばしたすべての支払いです。** だから省略可能な項目はありません（「記録に何が書かれるか」を参照）。

### H6 — 着地

`hotfix/<hotfix-id>` を `main` から切り、`main` へ戻します。**そこから枝は決して切りません。** その後 `/hora` が、開いている `release/<version>` を新しい `main` に追従させます。

---

## 断らずに、選択肢を出します

**断りません。** 夜中の3時に「できません」と言われても誰も助かりません。**あなたの不具合に対する**実際の代替案 — 実際のファイル名と実際の変更 — を組み立ててから、3つの選択肢を出します。

```
1. コードだけの修正を今出す（たいていはこれ）
     露出を止める、悪い書き込みを止める、防御を足す。
     破壊的な半分は次のバージョンへ

2. patch を上げた release/<version> でやる
     通常経路。遅いが、ちゃんと検収される

3. hora の外で人がやる          （破壊的なスキーマ変更のときだけ）
     キットは門を通したふりをしません。
     誰が決め、何をしたかだけを記録に残します
```

**代わりに選ぶことはしません。**

3 は意図して用意しています。通り抜ける道の無い門は、人が迂回する門であり、そうなると何も記録に残りません。

---

## スキーマ変更

問うべきは「マイグレーションが要るか」ではありません。**「DB を戻さずにコードだけ戻せるか」**です。戻せるなら、そのマイグレーションはリリースと切り離されており、一緒に出せます。

**3つすべてを満たすこと:**

1. **後方互換** — いま本番で動いているコードが、マイグレーション適用後もそのまま動く
2. **無損失** — 既存のものを落とさない・改名しない・狭めない・上書きしない
3. **時間の明記** — 実行時間とロックの挙動を、実際の行数に対する数字で述べてある

3は形式的な手続きではありません。書き込みを1時間止める `CREATE INDEX` は、2時間で出す修正としては失敗しています。

3つとも満たすなら、マイグレーションを先に出してコードを後から出せるので、原子的なデプロイが要らなくなります。

| 起きていること | 一緒に出せるか |
|---|---|
| カラムが小さすぎて書き込みが落ちている | **出せる** — 広げるだけ |
| インデックスが無く DB が溶けている | **出せる** — オンライン DDL。ロック時間を測って記録 |
| 一意制約が無く重複行が増え続けている | **半分** — コード側の防御を今。制約は既存の重複を掃除してから |
| カラム名を間違えた | **半分** — 新カラムを足して両方に書くのを今。古い方を落とすのは後 |
| 漏洩したカラムを消したい | **半分** — 露出を止めるのを今。削除は計画された作業 |
| 本番データが壊れている | **出せない** — そもそもマイグレーションではありません |

**破壊的な半分は、決して hotfix に乗りません。** ほとんどの場合、出血を今止めるコードだけの等価物があります。

**壊れた行の修復はマイグレーションではありません。** マイグレーションファイルは全環境で永久に再生されます。修復は、人が実行し、バックアップから戻せる一回限りのスクリプトでやります。

## 記録に何が書かれるか

```markdown
# Hotfix — session-expiry-blank

<!-- landed: 2026-08-23 -->
<!-- touches: attendance, sign-in -->
<!-- reproduced: yes -->
<!-- suites: full -->
<!-- data-damage: none -->
<!-- deferred: acceptance review, live run, UX audit, scenario list -->
<!-- debt: open -->

## What "fixed" means
<H1 で書いた1文>

## What backs this
- <テスト> — 修正前に落ち、修正後に通る
- ユニット全量: backend 214 passed, frontend-employee 51 passed

## What was skipped
このコードは検収されていない。…
```

**判定語は `landed` で、`passed` ではありません。** `passed` は `/hora-accept` のものであり、hotfix の記録が検収と取り違えられてはいけません。

**`touches:` には、変更したファイルが属する feature が入ります。** 実行時に組み立てて、書く前にあなたに見せます。後でどの検収をやり直すかを決める行だからです。

---

## 負債は普通の作業として戻ってきます

新しく何かを止める仕組みは足していません。**負債は、既存の門が既に扱い方を知っている作業に変換されます。**

```
次の /hora        未返済の負債を、名前とリンク付きで全部報告する

次の /hora-plan   touches: に並んだ feature それぞれについて、checkpoint 18 を
                  [ ] に戻す — 計画側のエントリも一緒に。そして debt: closed を書く
```

あとは通常経路です。`/hora-build` がその feature を拾い、`/hora-accept` が本来の reach で受け入れ、**それが通るまでバージョンは完了できません。**

**つまり hotfix はタダではありません。** 使うと次のバージョンの作業が増えます。これが、hotfix が全員の常用経路になることを防いでいます。

---

## 知っておくとよいこと

- **hotfix は一度に1つ。** 2本が同時に `main` へ向かうと、追従の筋道が一気に追いにくくなります
- **`/hora-hotfix` は `specs/` に書きません。** `/hora-spec` と `/hora-plan` 以外のすべての skill と同じで、仕様の問題は報告するだけで直しません
- **ユニットテストを狭めるには理由の明記が必要**で、共有コードに触れた場合は許されません
- **hotfix の PR タイトルにバッククォート付きのバージョンがあると `main` にタグが打たれます** — リリースのワークフローがタイトルを読むためです。バージョンは入れないでください

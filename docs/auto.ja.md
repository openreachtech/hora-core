# 自動経路

*[English](./auto.md)*

仕様書はできあがっています。どの節も読まれて承認され、ステージ7も通りました。残っているのは建てることだけです。それでも通常の経路では、ここから何週間も対話が続きます。`/hora-plan` は見つけた穴について尋ね、18の関所のうち4つは、機能ごとにユースケースを人と一緒にたどります。

`/hora-auto` は、その対話を抜いた経路です。**実装に入る前に、何を重視するかを一度だけ宣言します。そこから先は誰にも何も尋ねず、`release/<version>` を push して `main` への draft の pull request を出すところまで進みます。** `/hora` なら人に尋ねていた箇所は、すべて宣言に沿って決め、あとから読める場所に書き残します。

```
/hora        仕様書  →  計画（尋ねる）  →  18の関所、うち4つが尋ねる  →  掃引  →  人がマージ
/hora-auto   仕様書  →  宣言を一度  →  残りはすべて記録しながら  →  draft PR  →  人がマージ
```

**`/hora` に事前条件を1つ足したものです。** skill も関所も verifier も検収も同じです。変わるのは、検査が出した問いを誰が決めるかだけです。

## いつ使うか

**仕様書がステージ7を通ったあとです。その前には使いません。** 仕様書は意図であり、意図は、人が文面を読んだうえでしか書かれません。`/hora-auto` は `specs/` に書き込まず、`/hora-spec` も走らせません。ステージ7を通っていない仕様書は、実行がひとりで埋めることになる穴を、まだ一度も調べられていません。だから skill は、そういう仕様書では始めません。

**進行中に答えるより、結果をまとめて確かめたいときです。** 実行があなたの代わりに下した判断は、すべて question として残り、あとから読み、答え、覆せます。諦めるのは、変えるのがまだ安いうちに、1つずつ舵を取る機会です。

**その場にいない誰かの判断が要るときには向きません。** 画面を承認する必要のある顧客、呼び出す API を持っている別のチーム — 実行はその人たちにも尋ねられません。そういう穴はすべて安全な側に倒して先へ進みます。それが正しいことは多いのですが、尋ねたことには決してなりません。

## 変わらないもの

| | |
|---|---|
| **変わらない** | `/hora-setup`、`/hora-plan`、`/hora-build`、`/hora-accept`、`/hora-hotfix`。18の関所とそれぞれの通過条件。すべての verifier、監査、テストスイート。ブランチとコミットの規則すべて |
| **置き換わる** | 仕様書のあとの対話すべて。宣言に沿って下し、記録する判断に置き換わる |
| **加わる** | 宣言、事前点検、記録ファイル1つ — `.hora/tasks/<version>/_auto.md` — すべての停止に共通の表示、そして実行の終点 |

**検証については何も変わりません。** 関所はすべて走り、通過条件はすべて満たす必要があり、掃引は full で走ります。宣言は検査を足すことはでき — `test-depth` を上位に置けばテストケースが増えます — 減らすことは決してできません。

**機能を建てるスケジューラは、どちらでも構いません。** 宣言の中で `/hora` か `/hora-fast` を選びます。関所1・2・9・11で答える人がいないので、`/hora-fast` がどうしても縮められなかった対話の時間がなくなります。2つを組み合わせるのが、版をいちばん速く通す方法です（[`parallel.ja.md`](./parallel.ja.md)）。

## 宣言

**実行が行う、ただ一度の対話です。** 数分で終わり、順位を付けた一覧が `_auto.md` に書かれて終わります。

1. **選択式の質問が3つ。** プロジェクトの性格 — 社内向けの業務システム、一般向けのサービス、デモや検証、規制の厳しい業務 — と、どのスケジューラを使うか、期日があるかどうか
2. **順位の下書き。** 性格が出発点の序列を決め、仕様書がそれを動かします。各行には、仕様書のどこから来たかが添えられます。下書きは提案であって、読み取った事実ではありません
3. **自分の言葉で直す。** 「セキュリティを一番に」「見た目はそこそこでいい」「auditability を2の下に」。観点がどのキーで登録されているかを知っている必要はありません
4. **尋ねるのは、仕様書が順番を決められなかった組だけ。** `simplicity` か `extensibility` か、`delivery-speed` か `completeness` か — それぞれ二択で、仕様書がすでに決めているなら飛ばします

```
以下の序列がそのまま優先順位になります。

👍 1. data-integrity
👍 2. access-control
👍 3. auditability
👍 4. usability
👍 5. delivery-speed

📝 候補: observability, operation-safety, error-experience
   上の序列には入っていません。more で続きを表示します。

────────────────────────────────

👎 除外: i18n, seo
   この観点のためだけには作りません。
```

**重みではなく、順位です。** 重みだと、「高」が3つあったとき、そのうち2つが引き合った場面で実行は行き場を失います。順位には同順がないので、どの引き合いにも答えがあります。

**除外は、言葉の印象より弱い指定です。** その観点のためだけには作らない、という意味です。上位の観点が、除外した観点の仕事の一部を必要とするなら、その部分は作ります。仕様書が2言語を求めていれば、`i18n` について何と言っても2言語になります — その食い違いは、実行が始まる前に指摘されます。

**最後の画面には印がありません。** `_auto.md` に書かれる文面をそのまま見せます。承認が守るのは、書かれる言葉をあなたが読んだという事実だからです。

観点は34個、7つのグループに分かれています。[`priorities.md`](../kit/skills/hora-auto/references/priorities.md) に、すべての観点と、それが変える判断、倒す向きが載っています。

## 事前点検

**あなたがまだその場にいるうちに行う、最後の作業です。** 実行が必要とするコマンドを、害のない形で一度ずつ実行します。あとで実行を止めるものがあるなら、直せる人の目の前で、今止まるようにするためです。確かめるのは、各リポジトリの git、それぞれの remote、dry-run の push、`gh auth status`、パッケージマネージャ、環境の起動コマンドです。

**Claude Code の権限確認が出るかもしれないコマンドの前には、🔐 を付けた行で、そのことを知らせます。** その行の下に出る確認は、hora ではなく Claude Code が尋ねているものです。そこで「今後は確認しない」を選んでおくことが、あとで人なしで実行を続けられる理由になります。skill が権限の設定を自分で書くことはありません。Claude Code に何を無確認で実行させるかは、あなたが許可することです。

**点検が1つでも通らなければ、実行は始まりません。** remote のないリポジトリ、ログアウトしている `gh`、起動していないデータベース — どれも、終わりになって見つかるより、今直すほうが安く済みます。表示はほかの停止と同じ形ですが、見出しは 🚨 ではなく `🚫 自動実行を開始できません` です。まだ何も走っていないので、止まったのではなく、始まっていないからです。

**新しいプロジェクトでは、環境の確認が少し後になります。** リポジトリは、経路の中で `/hora-setup` が走るまで存在しません。なので最初の事前点検では環境の行を保留にし、セットアップが起動のしかたを記録したところで、計画に入る前に環境だけを確かめます。そこで通らなければ、🚫 ではなく 🚨 で止まります。セットアップがすでに作業をしているからです。

**事前点検は、再開のたびにもう一度行います。** 実行が待っている間に、環境が止まったり、ログインが切れたりしているかもしれないからです。

## 人なしでどう決めるか

**人に尋ねていたはずの問いは、すべて3つの種類のどれかに入ります。** 種類が、何が起きるかを決めます。

| 種類 | 何か | 実行がすること |
|---|---|---|
| **読み方** | 仕様書が2通り以上に読める | 最上位の観点に沿う読み方を取り、記録する（`auto-reading`） |
| **穴** | 埋めると、仕様書が述べていない意図を述べることになる — 誰が何を見られるか、何をもって検収とするか | **後で緩めやすい側に倒し**、目立つ形で記録する（`auto-default`） |
| **停止** | 実行が何を決めても解決しない | その機能だけ、または実行全体を止める |

**後で緩めやすい側、というのが2つめの種類の考え方のすべてです。** 仕様書が述べていない権限は、ユースケースが必要とする役割にだけ与え、それでも決まらない部分は最上位の役割だけに限ります。この推測が外れても、見られるはずの人がまだ見られないだけで、あとから与えるのは1行です。逆の推測は、見せてはいけない人にデータを出してしまい、それは取り戻せません。論理削除、データベースの制約、履歴を残すこと、個人情報を保存しないこと — 観点ごとに、同じ規則です。

**どの種類も `specs/` には書きません。** 読み方と穴は、どちらも実行を続けたうえで、`.hora/questions/<version>/open.md` に question として残ります。答え方はほかの question と同じで、仕様書を直します。次の `/hora-plan` がその変更を取り込みます。

**穴はすべて、すべての pull request の冒頭に並びます。** 閉じた側に倒すことが安全なのは、アクセスが必要だった人を閉め出していないかを、誰かが確かめる間だけです。それを確かめるのにいちばんよい立場にいるのは、マージする人です。

## 止まるとき

**止まり方はいつも同じ形で表示されます。** 止まった洗濯機の表示窓と同じで、止まった事実とコード、そのあとに、なぜ止まったか、どこまで進んだか、どう再開するか、が続きます。

```
🚨 自動実行を停止しました  [E-ENV]

原因
  backend の DB に接続できません（#payroll、checkpoint 6 のテスト中）
  試したこと: 記録済みの起動コマンドで 1 回立ち上げ直した → 接続できず

どこまで進んだか
  1.0.0     11 機能のうち 4 機能が完了
  作業中    #payroll  checkpoint 6 / 18。未コミットの変更なし
  止めた機能 ⛔ #bonus  [E-NPM]  Q12
  remote    まだ何も push していない

再開の手順
  1. backend の DB を起動する
  2. /hora-auto を実行する（/hora でも auto モードで再開します）。続きから自動で再開します
```

| コード | 止まった理由 |
|---|---|
| `E-SPEC` | 仕様書そのものを変える必要があり、それができるのは `/hora-spec` だけ |
| `E-SETUP` | セットアップが、何も決められない値を必要としている。または stack handbook に答えがない |
| `E-ENV` | 一度立ち上げ直しても、環境が応答しない |
| `E-NPM` | 一度再試行しても、install、update、audit が失敗した |
| `E-RETAKE` | 1つの機能の検収が3度失敗した |
| `E-GIT` | `main` の取り込みに判断が要る。または push が拒否された |
| `E-AUTH` | `gh` がログアウトしている。または権限確認に答えられなかった |
| `E-BLOCKED` | 残りの機能がすべて止まっている。それぞれを元のコード付きで並べる |
| `E-INTERRUPTED` | 前回の実行が、表示を出さずに途切れた |
| `E-UNCLASSIFIED` | 上のどれでもない — そして、この表に行が足りないという合図 |

**すべての停止が、すべてを止めるわけではありません。** インストールできない依存は、それを必要とする機能だけを止め（⛔）、実行はほかの機能で続きます。環境が落ちていれば、どの機能もそれを必要とするので、実行全体が止まります — 電源の切れたプリンターは、すべての印刷を止めます。**実行の途中で止めた機能は、終わりになっても止まったままです。** それが解消するまで、版は pull request に届きません。

**「試したこと」は、あなたが同じことを繰り返さないためにあります。** 実行は環境を一度だけ立ち上げ直し、依存を一度だけ再試行し、それ以上はしません。別のパッケージに差し替えることも、quarantine を外すこともしません。何を試したかも、何を試さなかったかも、表示に出ます。

**失敗は数えるだけで、比べません。** 検収が3度失敗した機能は、3回の失敗が同じでも違っても止めます。同じかどうかはどちらにも言いくるめられるので上限の条件にはならず、抜け道のある上限は、止めるためのループを止めません。代わりに3回の失敗を並べます。3回とも同じなら、誰も下していない判断があることが多く、毎回違うなら、1つ直すたびに別の場所を壊す設計であることが多いからです。

**進捗にも印が付きます。** 🟢 の行はマイルストーンです — 関門のマージ、機能の検収、掃引の合格。⛔ の行は、実行が続く中で1つの機能を止めたことを示します。それ以外は、関所ごとに印のない1行です。

## 再開と一時停止

**停止は、次の実行が始まる場所です。** 表示が示したものを直し、`/hora-auto` を実行します。`_auto.md` は `auto: on` のままなので、何も尋ね直しません。事前点検を行い、版の続きを進めます。そういう版では、`/hora` もまったく同じように動きます。

**使用量の上限に当たるのは、珍しいことではありません。** 自動の実行は誰にも歩調を合わせないので、ほかのどの実行よりも多く使います。実行が理由を言う前にセッションが終わると、次の実行がそれに気づき — `auto: on` で、停止の記録がない — 続ける前に `E-INTERRUPTED` を表示します。**原因を知っているとは主張しません。** 使用量の上限、閉じたターミナル、スリープしたマシンは、同じファイルを残すからです。

**途切れても、何も失われません。** チェックボックスは関所を通った瞬間に書かれ、途中で切れた関所は、すでにあるコードに対して最初からやり直されます。これが、この手法全体が拠って立つ再入可能性です（[`architecture.ja.md`](./architecture.ja.md)）。

**実行中に言えることが3つあります。** 動いているセッションに打ったメッセージは、ターンの途中で届きます。

| 言うこと | 起きること |
|---|---|
| 「pause」 | 進行中の関所を終えてから、⏸️ `PAUSED` で止まる。再開は、ほかの停止のあとと同じ |
| 「セキュリティを一番に」 | ここから先の宣言が直る。すでに下した判断はそのまま |
| 「stop auto」 | `/hora` と同じく、あなたに尋ねる形に戻る。すでに記録した判断は、すべて開いたまま残り、あなたが決める |

**Claude Code 自身の中断（Esc）も使えますが、関所の終わりを待ちません。** そうして中断した実行は `E-INTERRUPTED` として戻り、そのとき入っていた関所を最初からやり直します。

## どこで終わるか、なぜそこか

**`main` へのマージは、デプロイそのものです。** 版にタグを付け、世に出します。だから実行は、その直前で止まります。

1. マージ以外の、版の完了条件がすべて満たされ、止めた機能が1つもない
2. `main` をもう一度取り込む。hotfix が入れば、掃引が動かしたコードが変わるので、push の前に掃引をやり直す
3. 宣言されたすべてのリポジトリと app で `release/<version>` を push する
4. それぞれに `main` への draft の pull request を出す。冒頭にすべての穴を並べ、app のものには最後にマージすることを書く
5. `✅ 自動実行を完了しました  [DONE]`

**マージする人が、リリースする人です。** マージまで進む実行は、誰も見ていない版を、意図について下した推測ごと世に出すことになります。draft で止めれば、その1つの判断は、あるべき場所に残ります。「やっぱりここを直しておきたい」は、マージする瞬間まで可能なままです。

**`/hora-auto` を起動することが、その push とその draft への許可であり、それ以外への許可ではありません。** `--force` も、ほかのブランチも、ready にした pull request も、マージも、決して含みません。

## 何を諦めるか

| 諦めるもの | 代わりに立つもの |
|---|---|
| 仕様書の穴を、見つけるたびに人が決めること | 宣言に沿った判断。question として記録される |
| 何のためのものかを知っている人と、ユースケースをたどること | 同じたどり方を、メインセッションだけで |
| プロジェクトとして許容すると決める指摘 | 修正か、機能の停止 — 選ぶ人がいないので |
| 版が進めないときに `/hora` が示す出口 | 同じ選択肢を停止表示に。誰も選ばない |

**この取引は、あとで読む場所に書いてあります。** `_auto.md` には、宣言したこと、その変更、すべての停止があります。`open.md` には、あなたの代わりに下した判断が、その種類のまま残っています。

## 知っておくとよいこと

- **ほかの skill は、会話ではなく `_auto.md` を見て auto モードだと知ります。** コンテキストが要約されたり、新しいセッションになったりすると、実行がどう始まったかは忘れられます。ファイルは忘れません
- **`_auto.md` は削除されません。** 停止や一時停止の間は `on`、あなたが切れば `off`、終点で `done` になります。1つの版のもので、次の版は、あなたがその版で `/hora-auto` を起動したときだけ自動で走ります
- **`/hora-setup` は、このパッケージではなく boilerplate が同梱しています。** セットアップが止まって尋ねるはずの場面では、自動の実行は `E-SETUP` で止まります
- **宣言は仕様書ではありません。** 仕様書が開けたままにしたことだけを決め、そこに書かれたものは、誰かが満たすべき要件ではありません

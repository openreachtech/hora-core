# 文書の文体

*[English](./document-style.md)*

人が読む文書がどう書かれるかを定めます。**もう半分は [`writing-style.ja.md`](./writing-style.ja.md)** で、そちらは `kit/` 配下 — エージェントが実行時に読むファイルです。

2つを隔てているのは費用です。skill ファイルの規則は実行のたびに支払われるので、あちらの3つの規則はすべて圧縮についてのものです。ここにあるものは実行時に読まれないので議論に費用がかかりません。ただし、その中にある主張を読者が見つけられなければ、やはり失敗です。

---

## 対象

キットの全リポジトリの `README.md` と `docs/` 配下すべて、両言語ぶん。`specs/` は対象外です（プロジェクトが自分のために書くもの）。`kit/` も対象外で、そちらは `writing-style.ja.md` のものです。

---

## 読者は、自分の意思でこれを開いた

手順を実行しているエージェントではありません。問いを持って来て、答えを得たとき、あるいは「ここには無い」と思ったときに去ります。

**したがって予算は長さではなく、見つけやすさです。** 論拠を述べること、退けた代案を示すこと、その規則が防いでいる失敗を名指すこと — ここではそのすべてが場所に値します。値しないのは、読者が4つの節から組み立て直さなければならない主張です。

---

## 太字は、見落としてはならないものを示す

**太字にするのは、命令、禁止、あるいは流し読みする読者にも持ち帰らせたい唯一の事実です。段落の主題は太字にしません。** それは見出しの仕事です。これが規則で、この節の残りは「破れているかどうかをどう見分けるか」です。

散文で、節あたり概ね2つ。**これは目安であって上限ではありません** — 並列する禁止事項を3つ持つ節は欠陥ではなく、すべての段落が太字で始まる節は何も示していません。2を超えたら点検の合図で、超過分はほぼ必ず段落の主題です。

数は skill 側と同じで、理由は違います。あちらでは太字がトークンを費やし、こちらでは太字が自分の意味を費やします。

**ラベルは数に含めません。** 表のラベル列、段落が扱う条件（`Under as-built`）、UI の操作経路、そして用語を用語として示すもの（`carry-over`、`resolved`）— いずれも太字は名前とその説明を隔てており、強調ではなく構造です。このキットは一貫してそう使ってきましたし、日本語では斜体が使えないので他に手がありません。

このキットを散文だけで実測すると、太字は節あたり 0.1 から 3.8 まで振れています。46文書のうち14が2を超えており、超過分はそのすべてで段落の主題でした。

---

## 1文につき1主張

**語数の上限は設けません。** skill ファイルでは許されない長さの文が、ここでは許されます。論拠こそが主題だからです。

してはならないのは、1つの文が2つ目の主張を運ぶことです。**2つ目の主張をつなぐ em ダッシュは、文の区切りです** — skill 側と同じ規則で、理由も同じです。これは費用ではなく構文解析についての規則だからです。

ここでのダッシュには3つの用法があり、区切りに当たるのは3つ目だけです。

| 用法 | |
|---|---|
| **対で挿入句を閉じる** | `ワークフローは — 5本すべて — 同じ式を持ちます`。間の材料を取り除いても文は成立します。2本ではなく1つの印です |
| **後置のダッシュ** | `…4つのパッケージ — ドメインごとに1つ`。句点まで走る挿入句を開きます。1つの印です |
| **独立した節をつなぐ** | `人は覚えている分を書き — 残りの沈黙が「そこには何も無い」と読める`。2主張です。**これが区切りに当たります** |

したがって、ダッシュを数えても何も見つかりません。このキットを実測すると、ちょうど2本の文が116あり、そのほぼすべてが対です。3本以上は5文で、そのうち節をつないでいたのは1文でした。**数ではなく文を読んでください。**

## 日本語版は翻訳ではない

同じ文書を日本語で書いたものです。日本語だけを読む人が、劣った版を読んでいることになってはなりません。

- **ラテン文字とその前後の日本語の間には空白を入れます** — `Hora Kit が` であって `Hora Kitが` ではありません。インラインコードと識別子もラテン文字として扱います。
- **括弧は全角です**。`（…）` であって `(…)` ではありません。
- 英語版が英語のまま述べている用語は、英語のままにします。`resolver` や `checkpoint` に日本語を作りません。
- 英語版が論じているところでは、日本語版も論じます。片側だけを要約するのが、対が食い違い始める入口です。
- **日本語では斜体が読めないので、太字が代わりを務めます。** したがって日本語版の太字は英語版より多くなり、数を揃える必要はありません。`*works*` は `**動くかどうか**` になります。

---

## 文書とその対は、1つの決定である

同じコミットで編集し、件名は拡張子を落として文書を名指します — `Kick out the registry setting from README`。

**見出しの構造は両言語で同一です。** 同じ階層、同じ順序、同じ個数。図・表・コードフェンスは、両方に現れるか、どちらにも現れないかのどちらかです。

---

## skill の名前の書き方

skill は **呼び出しに使うスラッシュを先頭に付け、バッククォートで囲みます** — `/hoc-git-commit` であって `hoc-git-commit` ではありません。スラッシュが無いと、その文字列はディレクトリ、パッケージ、あるいはブランチの接頭辞と区別できません。このキットにはその3つがいずれも大量にあります。

**規約を指すときは、ファイル名ではなく skill の名前で示します。** 他パッケージの中のファイルは、このリポジトリがリンクしてよいものではなく、そのパスは相手のパッケージが変えてよいものです。「`/hoc-git-commit` スキルの `granularity.md`」と書き、読者には skill 経由で辿らせます。

---

## 構造

| | |
|---|---|
| **言語リンク** | `# ` 見出しの直下に `*[English](./x.md)*` を単独行で。その上の HTML コメントは編集する人のためのもので、この行は読む人のためのものです |
| **目次** | 概ね200行・15節を超えたら置きます。トップレベルのみ。コードフェンス内の見出しは節ではありません |
| **末尾** | `## 次に読むもの`。問いと行き先の2列の表にします |
| **図** | その図が描いている主題を論じている場所に置きます。それ以外の場所に置いた図は装飾です。このキットには誘惑されるだけの図が揃っています |
| **リンク** | `README` は絶対 URL で張ります。npm がこのツリーの外で描画するからです。`docs/` 配下は相対リンクにします |

---

## ここで定めていないもの

| | |
|---|---|
| 実行時に読まれる `kit/` 配下のファイル | [`writing-style.ja.md`](./writing-style.ja.md) |
| 1つのコミットに何が入るか、およびそこにある対の規則 | `/hoc-git-commit` スキルの `granularity.md` |
| 識別子・略語・綴り | `/hoc-naming` スキル |
| そもそもその文書が必要かどうか | 何も定めません。それは判断であり、あなたのものです |

# 並列経路

*[English](./parallel.md)*

版には機能が11個あり、期日は3週間後、前の版の実測では機能1つに4日かかっています。通常の経路 — 機能を1つ、18の関所に通して検収し、次へ — は正しい経路ですが、この期日には収まりません。

`/hora-fast` はそのためのもう1本です。**機能が共有する部分を先に建て、そのあと機能同士を横に並べて、それぞれ専用の git worktree で建て、最後に版全体を一度だけ実際に動かして検証します。** 仕様書、計画、機能ファイル、検収記録は `/hora` が書くものとまったく同じなので、どちらのスケジューラも、もう片方が始めた版を引き継げます。

```
/hora        機能1つ  →  18の関所  →  検収  →  次の機能
/hora-fast   共有ファイルを一度  →  機能を横に並べて、それぞれ18  →  最後に掃引を一度
```

**`/hora` はこれを起動しません。** 期日のために並列で建てるかどうかは人が決めることなので、`/hora-fast` は自分で打ちます。

## 効く場合、効かない場合

skill は何よりも先に計算をします。実測した機能1つあたりの速さ × 残りの機能数を、残り日数と比べます。**収まるなら、そう言って `/hora` を走らせます。** 並列で建てることには後述の代価があり、直列で収まる版がそれを払う理由はありません。

速さは、各関所の行が持つ実行記録から取ります — `wall-time:`、関所に入ってから印を付けるまでの秒数です。18のうち4つは対話です。1・2・9・11 はユースケースを人に確認する関所で、その `wall-time:` の大半は人が答えている時間です。

**この4つは、どちらのスケジューラでも同じ時間がかかります。** エージェントは横に並んで走れますが、人は質問に1つずつ答えます。時間の大半がこの4行に乗っている版は `/hora-fast` で何も得られず、記録がそう示すときは skill もそう言います。

## 変わらないもの

順序以外のすべてです。

| | |
|---|---|
| **変わらない** | `/hora-spec`、`/hora-setup`、`/hora-plan`、`/hora-accept`、`/hora-hotfix`。18の関所とその終了条件。機能ファイル、実行記録、検収記録。ブランチとコミットの全規則。3つの不変条件 |
| **置き換わる** | `/hora` の「機能を1つ検収まで通してから次へ」 |
| **加わる** | 土台、機能ごとの worktree、マージ工程、drain、記録ファイル1つ — `.hora/tasks/<version>/_fast.md` |

**2つのスケジューラを入れ替え可能にしているのは機能ファイルです。** `/hora-fast` は、`/hora-build` が書いたはずの18のチェックボックス、同じ印、同じ実行記録を書きます。だから `/hora` は、`/hora-fast` が半分建てた版を「いくつかの機能が済んだ普通の版」として読みますし、逆も同じです（後述の「2つの切り替え」）。

関所は `/hora-build` とまったく同じ手順で走ります — 同じ skill の照合、同じエージェント、同じ verifier。違いは1つ、その機能の worktree の中で走ることです。

## 土台

`/hora-build` は1つの関所の単位をすでに横に並べて走らせており、それを安全にしている規則は排他性です。2つの単位が両方書くファイルは、どちらか一方のものにする。**`/hora-fast` は同じ規則を1段上に持ち上げます。2つの機能が両方書くファイルは土台のものにし、土台はどの機能よりも先に、一度だけ建てます。**

| 土台に入るもの | どこで分かるか |
|---|---|
| サーバごとの契約 | `/hora-plan` がすでに導出し、固定している |
| 複数の機能が読み書きするテーブル | 仕様書のデータモデル |
| 契約から生成される型 | 装備されているスキーマ系の skill |
| conflict-proof なファイルへの計画済みの変更 — 環境変数のキー、compose のプロファイル、`Base` のメンバー | `/hora-build` が「関所が単独で編集してはいけない」と定めているファイルの一覧 |
| 計画の時点で見えている依存 | 仕様書の key file map と stack handbook |
| 全機能が読むマスター行 | seed |
| `/hora-plan` が複数の機能ファイルに `Conflict:` の印を付けたファイル | 機能ファイル |

土台は main の作業コピーで、`release/<version>` の上に、機能と同じ関所と同じエージェントで建てられ、最後に2つの検査で終わります。**宣言された契約・生成された型・スタブの機械的な照合**と、先端での全リポジトリのテストスイートです。照合があるのは、並列の転記が黙ったずれで失敗するからです — 3つの成果物がそれぞれ単独では正しく、互いに違っている。文章はそれを捕まえられません。

**土台は先端に対して導出されるので、`/hora` が始めた版ではその大半がすでにあります。** 先に済んだ機能が建てたテーブルは、土台の作業ではなく、済んだものです。

## 機能ごとに worktree を1つ

[`architecture.ja.md`](./architecture.ja.md) の「なぜ直列なのか」に問題が書き残されています。1つの作業ディレクトリには1本のブランチしか置けないので、1つのツリーに2つの機能を入れると、それぞれのコミットを持てません。**git worktree は機能ごとに専用のディレクトリを与え、この問題を消します。** ブランチは変わらず `feature/<feature-id>` で、`/hora-build` が切る場所で切られ、`commits.md` がマージする場所でマージされます。変わるのは、それが main の作業コピーではなく `.worktrees/` の下に住むことです。

```
<project>-app/
  <project>-backend/                            main の作業コピー。release/<version> にいる
  .worktrees/attendance/<project>-backend/      feature/attendance
  .worktrees/payroll/<project>-backend/         feature/payroll
  .worktrees/payroll/<project>-frontend-admin/  feature/payroll の frontend 側
```

「リポジトリの中から」と言う規則はすべて、worktree をそのリポジトリとして読みます。lint、テスト、change set の導出はそこで走り、進行中の機能のコマンドを main の作業コピーで走らせるのは、[`structure.md`](../kit/skills/hora/references/structure.md) がすでに警告している「作業ディレクトリ違い」の失敗です。

**2つめの作業コピーには専用の依存、データベース、ポートが要り、それが何かは stack handbook の答えです。** `/hora-fast` は必要なものを述べ、実行時に読む handbook がその方法を答えます。handbook に答えが無ければ、推測せずに `lacked-environment` の質問で止まります。

同時に開く機能の数は人が決める上限で、既定は3です。マシンの負荷とメインセッションの注意力を抑えるための数で、正しさはこの数に依存しません。

### マージ工程

機能のゲートが終わると — backend は関所9、frontend は関所17 — そのブランチはいつも通り `release/<version>` にマージされます。他の機能が進行中なので、3つのことが続きます。

1. メインセッションが、先端のすべての集約ファイルをフォルダの走査から再生成する
2. 契約の照合と、そのリポジトリの全テストスイートを先端で走らせる。**ここで赤くなったら、原因の持ち主は名指しできます。** マージした機能のファイルは排他なので、その機能を、それを作った関所へ戻します
3. 他の worktree はそれぞれ、自分の次のマージのときに新しい先端へ rebase する

## テストを分けておく

[`hora-verifier.md`](../kit/agents/hora-verifier.md) はすでに、全機能のテストが1つのデータベースに対して、任意の順序で一緒に走っても耐えることを要求しています。`/hora-fast` はこの要求に何も足しません。効き始める時点を関所18から関所1に早めるだけです。N 個の機能のテストを分けておくのは、次の4つです。

| | |
|---|---|
| **機能ごとの帯** | `/hora-build` はすでに機能ごとに行 id の接頭辞を割り当てています。機能が seed する行も作る行も、その帯の中の id を持ちます |
| **2種類の seed** | 全機能が読むマスター行は土台にあります。機能自身の行は、その機能の seeder ファイルに、その帯で置きます |
| **総数を検証しない** | 「一覧は3行返す」は、他の機能が1行 seed した瞬間に壊れます。テストは自分の帯の中を検証します |
| **worktree ごとのデータベース** | 進行中のテストが、他の機能の書きかけの行を見ないためです |

**2つの機能のテストが最初に出会うのは、`release/<version>` でのマージ後のテストスイートです。** だからそれを、マージのたびに走らせます。

## 機能が証明するもの、版が証明するもの

**各機能の関所18は、`/hora-accept` がすでに定めているゲート実行です。全リポジトリのユニットテスト、シナリオ一覧、レビューの静的な検査 — ブラウザは無し。** 機能の最後のゲートがマージされたあと、先端で走ります。場所も reach も `/hora` が与えるものと同じで、同じ記録を書きます。これが2つのスケジューラのファイルを同一に保ち、機能がマージ1つ分の新しさのうちに指摘を拾います。

**版は、版全体の掃引で一度だけ実際に動かします。** full reach の `/hora-accept` — 環境、実際に実行した全テストスイート、全シナリオ、ブラウザを動かすレビュー、UX、セキュリティ、版自身の受入基準。この設計が寄りかかっている実行はこれです。ブラウザ無しのゲートには見えないもの — テーブルを埋める機能が横で建っていたために空の画面、2つの機能をまたぐ流れ — はここで見つかります。

指摘の行き先はいつも通りです。名指しされた機能の関所を解除し、`retake/` ブランチで建て直す — そして retake は、他の機能と同じように worktree を開きます。

## 2つの切り替え

2つのスケジューラは同じファイルを読み書きするので、変換するものはありません。揃えるべきは git です。`/hora` は main の作業コピーに機能を1つ置き、`/hora-fast` はそこに何も置きません。

**`/hora-fast` へ：いつでも。** `/hora` がゲート途中で残したかもしれない1つの機能は、未コミットの作業ごと worktree へ移されます — main のコピーで stash、`release/<version>` へ切り替え、その機能のブランチで worktree を作り、pop。コミットは1つも作らないので、パッケージのコミット規約に触れません。

**`/hora` へ戻る：先に drain。** 実行の中で「drain」と言います。`/hora-fast` は新しく何も開かず、進行中の全機能をいまのゲートの終わりまで進めてマージし、worktree を閉じます。`git worktree list` が `.worktrees/` の下に何も示さなくなれば、全機能がゲートの入口にいて、main の作業コピーはすべて `release/<version>` にいます — `/hora` 自身の開始状態です。

土台は `/hora` から何も必要としません。先端にあるコードであり、既存のコードに対して走る関所は、作るのではなく整合させます。

**drain を飛ばすと、大きく失敗します。** `/hora` は worktree の無い機能をいつも通り建て、worktree のある機能を初めて取った時点で git に止められます — worktree に checkout 済みのブランチは、もう一度 checkout できません。駐車された worktree は、`/hora-fast` が再び走るまで待ちます。

## 何を諦めるか

直列経路は、回帰を起こした実行でコミット1つ分の新しさのうちに拾い、次の機能を始める前に各機能の画面を動かします。`/hora-fast` はその両方を差し出します。

| 諦めるもの | 代わりに立つもの |
|---|---|
| 回帰を、起こした関所で拾うこと | マージ工程で拾い、マージした機能の排他なファイルから持ち主を特定する |
| 機能の画面を、その機能のゲートで動かすこと | 機能ごとの静的なゲート実行。全画面は掃引で一度だけ動かす |
| 人との対話が版全体に散らばること | まとまる。複数の機能が同じ時間帯に関所9へ到達する |
| 機能をまたぐ指摘が1つずつ来ること | 掃引でまとめて来て、それぞれが retake の worktree を開く |
| リポジトリごとに作業コピーとデータベースが1つ | 進行中の機能ごとに、もう1組 |
| `/hora-plan` が見落とした `Conflict:` の印 | 計画時の印の代わりに、マージ工程でのマージ衝突 |

**差し出したものは、次の実行が読む場所に書かれます。** `.hora/tasks/<version>/_fast.md` は、誰がスケジューラを選んだか、上限、土台を持ちます。飛ばした対話の関所は、機能ファイルのその行にあります。開いている worktree は git から読み、ファイルには写しません。

## 知っておくとよいこと

- **人が言えることは4つで、どれも引数ではありません。** 打つこと自体がスケジューラの選択。「3つずつ」が上限。「drain」が巻き取り。「#payroll の 9 を飛ばして」が、対話の関所を1つ、一度だけ、記録付きで飛ばすこと。名前の後ろに打った `/hora-fast drain` も同じ文として届きます
- **仕様書が無いあいだ、関所1は飛ばせません。** 検査を飛ばすのは検証を1つ諦めることで、仕様書を飛ばすのは仕様書を1つでっち上げることです
- **`.worktrees/` は hora リポジトリで ignore されます。** 入れ子のリポジトリと同じです。行が無ければ skill が足します
- **`main` へのマージは決して急ぎません。** マシンの外へ出る唯一の手順であり、並列実行が生む勢いこそ、この手順が抗うべきものです
- **hora のファイルは編集しません。** `/hora-build` の規則と同じに読める箇所は、そこへのポインタです

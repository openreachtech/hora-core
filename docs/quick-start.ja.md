# クイックスタート

*[English](./quick-start.md)*

始める前に仕様書を書いておく必要はありません。**やりたいことを `specs/1.0.0/request/` に、関連資料を `specs/1.0.0/annex/` に入れて `/hora` を実行してください** — そのバージョンにはまだ仕様書が無いので、`/hora` はまず `/hora-spec` を呼び出し、入れたものを材料にあなたと仕様書を策定するところから始めます。

材料になるのは、手元に実際にあるものです — メール、チケット、箇条書き1枚、誰かが描いたモックアップ、ER 図、古い設計書、実務が本当にそれで回っているスプレッドシート。整っている必要はありませんし、**あなたが文面を読んで承認するまで、どれも要件にはなりません。**

---

## 3つの手順

```
1. hora-boilerplate から <myproject>-app を作り、npm install

2. 手元にあるものをバージョンのディレクトリへ入れる
     specs/1.0.0/request/   このバージョンで作ってほしいこと
     specs/1.0.0/annex/     それを説明する関連資料
     specs/1.0.0/sources/   すでに内容が決まっている仕様の文書

3. Claude Code のプロンプトで /hora を実行
     まだ仕様書が無いので、/hora が /hora-spec を呼び出す
     /hora-spec は入れたものを読み、あなたと対話しながら
     仕様書を1節ずつ書き上げる
```

**準備は手順2 で終わりです。** その後はすべて対話です。

---

## 手順1 — リポジトリを作る

`<myproject>-app` は [`hora-boilerplate`](https://github.com/openreachtech/hora-boilerplate) テンプレートから作ります。作った `<myproject>-app` 配下で `npm install` すると、`/hora` を使うためのツール群が `<myproject>-app/.claude/` にセットアップされます。手順と、事前にインストールしておくものは、`hora-boilerplate` の README にあります。

**`specs/` の下はリリースの版ごとのディレクトリで、`specs/1.0.0/` が最初の版です。** 3つのディレクトリはテンプレートに空の状態で入っているので、手順2 の前に作るものはありません。

---

## 手順2 — 手元にあるものを入れる

| ここに入れると | `/hora-spec` がこう理解する |
|---|---|
| `specs/1.0.0/request/` | **これがこのバージョンで作ってほしいことだ。** アイデア、要望、やることの一覧 — それが筋の通ったものかどうかは、まだ誰も詰めていない |
| `specs/1.0.0/annex/` | **これは仕様を説明するだけのものだ。** モックアップ、画面デザイン、図、古い設計書、スプレッドシート |
| `specs/1.0.0/sources/` | **これは仕様そのものの一部だ。** 現行の要件一覧、API リファレンス — 誰かがその内容に責任を負えるもの |

**`request/` はやりたいことのため、`annex/` は関連資料のためのものです。** どちらに入れたものも、それ自体が仕様書の文面になることはありません — 提案か質問としてあなたに戻り、あなたが承認したものだけが書かれます。

意図して置くべきなのは `sources/` です。ここに置いて仕様書の `Sources` の節に宣言された文書は、仕様書そのものと全く同じに読まれます — `/hora-plan` がその中身からタスクを作り、`/hora-build` が実装します。だから、そこに入れた要望リストは、誰かが実装する要望リストになります。**迷ったら `annex/` へ。** 失われるものはありません。内容が本当に必要なら、対話を通って仕様書に入り、そこから機能になります。

ファイルを置くときに知っておくとよいことが4つあります。

- **バイナリファイルでも構いません。** PDF、PNG、書き出したモックアップ — `/hora-spec` はそれぞれを仕様書からリンクし、何を示すものかを1行添えます。絵に描かれたものが明文の要件であるかのように書き写されることはありません
- **どのファイルも必須ではなく、3つのディレクトリも必須ではありません。** 空でも `/hora-spec` は何も指摘しませんし、`specs/1.0.0/` 配下の別の場所に置いた文書も同じように見つかります — ただしその場合、置き場所からあなたの意図が読み取れないので、3つのどれなのかをファイルごとに質問されることになります
- **実装リポジトリの中へリンクしてはいけません。** 実装リポジトリとは、`<myproject>-app` の中に作られる、実際のコードのリポジトリです。gitignore されているので、そこへのリンクはあなたのディスクでは開けても、他の全員の clone では壊れます。必要なものは `specs/1.0.0/` へコピーしてください
- **持ち込めないものでも、存在を伝える価値があります。** wiki のページ、ドライブ、チケットトラッカー — `/hora-spec` は、自分の手が届かない場所に何があるかを尋ねます。最も役に立つ文書が、誰も言い出さなかったものであることは珍しくないからです

---

## 手順3 — `/hora` を実行する

```
/hora
```

**`/hora` は Claude Code のスキルです。** `<myproject>-app` で Claude Code を起動し、そのプロンプトに打ちます。

`specs/1.0.0/spec.md` がまだ空のバージョンでは、まず `/hora` が `/hora-spec` を呼び出します。自分で `/hora-spec` と打つのと同じことです。setup、計画、実装、検収 — この後も、Hora Kit で通常の作業を始めるときに入力するコマンドは `/hora` です。

`/hora-spec` はまず、渡されたものを読むところから始めます — これがステージ0 です。`request/` を最初に読み、次に `sources/` と `annex/`、そして `specs/1.0.0/` の残りを読みます。**あなたの置き方は、まとめられた「確認」として戻ってきます** — `sources/` の全体で1往復、`annex/` で1往復、`request/` で1往復 — ファイルごとの質問ではありません。文書が20個あっても3往復で、あとは置き場所を変えたいものについて1往復するだけです。

そこから7つのステージです — 最初にユースケース、次にこのリリースが何を積み何を積まないか、数字（利用者数や保持期間などの非機能要件）、データモデルと API、画面、セキュリティ、そして文書全体のレビュー。**各セクションは全文が示され、あなたが承認してはじめて `spec.md` に書かれます。** `/hora-spec` が自分で思いついたものは、提案という札が付いて出てきます。

**仕様書を書くこの段階には立ち会ってください。** 7つのステージはどれも対話で、機能名を並べただけのものが実際に作れる要件に変わるのはここです。この後の工程 — setup、計画、実装、検収 — は `/hora` が自動で進めます。答えが必要になれば、そこで止まって尋ねます。

## 入れたものが何になるか

| | `request/` | `annex/` | `sources/` |
|---|---|---|---|
| ステージ0 がそれをどう扱うか | **このバージョンの議題**として読む | **解釈のために**読む | `Sources` の節に宣言し、**仕様**として扱う |
| `spec.md` への入り方 | その話題を扱うステージで、提案と質問として | 対話の中であなたが是としたものを通じてのみ | 機能ファイルと全く同じに、抽出される |
| `spec.md` に宣言され、リンクされるか | **されない** | される | される |
| `/hora-plan` がタスクを抽出するか | **そもそも読まない** | しない | する |
| そのバージョンが書き上がった後 | **使い切られている** — 何が依頼されたかの記録 | 依然として説明 | 依然として仕様 |

**`request/` のファイルを `sources/` へ移してはいけません。** source は製品が何をしなければならないかを述べ、request は誰かが詰めてほしいと思っていることを述べます。移せば、`/hora-plan` がタスクを抽出する対象に要望リストが入ってしまいます。

**バージョンが書き上がっても、ファイルはそのままにしてください。** `request/` は「実際に何が依頼されたか」の記録で、後からその記録と出来上がった仕様書を読み比べることが、対話が何を変えたのかを見る方法です。

## 次のバージョンも始め方は同じ

```sh
mkdir -p specs/1.1.0/request
$EDITOR specs/1.1.0/request/csv-export.md   # 「管理者が1ヶ月分の勤怠を CSV で欲しい」
```

そしてまた `/hora`。3つのディレクトリが同梱されるのは `1.0.0` だけなので、次のバージョンでは必要なものを自分で作ってください。

**2つ目のバージョン以降、`spec.md` は1つ前のバージョンに対する差分です。** 対話から出てくるのは、その版自身の文書情報と新しい機能だけで、それ以外は書かれません。過去の版の `spec.md` に手が入ることはありません。

**資料は版ごとに、その版の中へ置いてください。** 1.1.0 でも必要な文書は `specs/1.1.0/` 配下に自分のコピーを持ちます。1つのファイルを両方の版から参照すると、1.1.0 のためにそれを編集した瞬間、1.0.0 が何に対して書かれたのかが黙って変わってしまうからです。

## この経路が飛ばしていないもの

**これは仕様書を「書く」ことの近道であって、仕様を「決める」ことの近道ではありません。**

| 飛ばしていないこと | 何がそれを担保するか |
|---|---|
| 入れたものが、それ自体で要件になることはない | 各セクションは全文が示され、あなたがその文面を承認してはじめて書かれる |
| 7つのステージはすべて実行される | その順序（ユースケースが先、画面は後）は規則であり、各ステージは通過条件を持つ関所である |
| その場で誰も答えられない質問は、推測で埋められない | `.hora/`（キットが記録を置くディレクトリ）に記録される。質問はどれも仕様の穴なので、答えるときは `specs/` を編集する |
